## Contexte
La table `sales` n'avait aucune politique RLS scoped. Seules des politiques `auth_*` et `role_*` permissives (USING/WITH CHECK = true) existaient, combinées en OR, ce qui neutralisait tout least-privilege. La table dispose d'une colonne `site_id` (comme la table `expenses`).

## Objectif
Ajouter RLS least-privilege sur la table `sales` : lecture par site pour les rôles staff, écriture (INSERT/UPDATE/DELETE) restreinte aux administrateur et gestionnaire sur leur site.

## Commands Executed

1. Création de `supabase/migrations/20261107010000_rls_sales_least_privilege.sql` :
   - `DROP POLICY IF EXISTS` pour `auth_select_sales`, `auth_insert_sales`, `auth_update_sales`, `auth_delete_sales` (migration 017, permissives)
   - `DROP POLICY IF EXISTS` pour `role_select_sales`, `role_insert_sales`, `role_update_sales`, `role_delete_sales` (migrations 012/028, trop permissives)
   - `CREATE POLICY sales_select_scoped` : SELECT pour authenticated, USING = staff roles + site_id match
   - `CREATE POLICY sales_write_scoped` : FOR ALL, USING = staff roles + site_id (lecture pour trouver la ligne), WITH CHECK = admin/gestionnaire + site_id (écriture)
   - `ALTER TABLE public.sales FORCE ROW LEVEL SECURITY`
   - Garde-fou DO block : vérifie FORCE RLS et l'absence de politique USING/WITH CHECK = true

2. Création de `tests/integration/rls-sales.test.mjs` :
   - `comptable peut LIRE les sales de son site` → 1 ligne retournée
   - `comptable ne peut PAS modifier une sale` → erreur 42501
   - `admin PEUT modifier une sale` → succès

3. `supabase db reset` échoue sur la migration pré-existante cassée `20261106230000_add_site_id_to_core_tables.sql` (référence `surveillance_events` inexistante) — problème pré-existant, non lié à ce travail.

4. Application manuelle de la migration via psql, puis exécution des 3 tests d'intégration RLS sales.

## Analysis
- Les anciennes politiques `auth_*` et `role_*` ont été correctement supprimées car elles se combinaient en OR avec les nouvelles politiques `*_scoped`, neutralisant le least-privilege.
- Le pattern `USING` inclut les rôles lisibles (comptable y compris) pour qu'un UPDATE trouve la ligne, puis `WITH CHECK` restreint à administrateur/gestionnaire pour lever 42501 au lieu de retourner 0 lignes silencieusement.
- `FORCE ROW LEVEL SECURITY` garantit que RLS s'applique même au propriétaire postgres.
