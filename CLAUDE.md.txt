# CLAUDE.md — BAHKANSO
## Instructions du projet et cadre de réalisation

Ce fichier définit le cadre commun de travail sur Bahkanso.

Il remplace les anciennes consignes de refonte limitée à sept pages.
Il n’autorise ni suppression générale des modules, ni reconstruction
complète de l’application, ni modification distante.

Une demande explicite plus récente de l’utilisateur peut ajuster
le périmètre. En cas de contradiction importante, la signaler avant
une action destructive ou un changement d’architecture.

---

## 1. MISSION ACTUELLE

Faire évoluer Bahkanso en une application agro-pastorale cohérente,
agréable et réellement utilisable.

Objectifs :
- conserver les modules métier existants ;
- généraliser les cartes retournables pour présenter les collections ;
- rendre les pages, formulaires et actions réellement fonctionnels ;
- réutiliser les mécanismes existants lorsqu’ils sont corrects ;
- corriger les défauts par lots limités et vérifiables ;
- préserver les données et les travaux en cours.

Ne pas confondre :
- présence de code et fonctionnalité vérifiée ;
- navigation vers une page et action sur un élément ;
- compilation réussie et validation fonctionnelle ;
- prototype visuel et fonctionnalité avec persistance.

Ne pas déclarer l’application entièrement fonctionnelle sans preuves.

## 7. DESIGN ET CARTES RETOURNABLES

### Direction générale

Conserver l’identité Bahkanso et l’organisation de l’application :
- menu latéral ;
- en-tête ;
- modules et sous-menus ;
- indicateurs ;
- actions de gestion.

Références de palette :
- vert agricole : #2D5016 ;
- vert d’interaction : #4A7C2E ;
- accent blé : #E8B923 ;
- terre : #8B6F47 ;
- fond crème : #FAF7F2 ;
- textes slate-800 / slate-500.

Ne pas appliquer une recoloration globale hors du lot autorisé.
Préserver la cohérence avec les composants existants.

### Collections

Les cartes retournables sont la présentation cible des listes
métier, à déployer module par module.

Une exception nécessitant un tableau doit être justifiée
et soumise à validation.

Ne pas transformer artificiellement en cartes retournables :
- les formulaires ;
- les menus ;
- les filtres ;
- les graphiques ;
- les indicateurs devant rester immédiatement visibles.

### Structure d’une carte

Recto :
- nom ou référence ;
- photographie ou icône pertinente ;
- statut lisible ;
- informations essentielles ;
- commande explicite pour afficher les détails.

Verso :
- informations complémentaires ;
- relations utiles ;
- actions pertinentes ;
- commande explicite de retour.

Contraintes :
- retournement volontaire, jamais automatique ;
- utilisation au clic, au tactile et au clavier ;
- focus visible ;
- face masquée non interactive ;
- boutons d’action indépendants du retournement ;
- pas d’information essentielle disponible uniquement au survol ;
- respect de la préférence de réduction des animations ;
- aucun texte coupé ni bouton inaccessible ;
- adaptation aux petits écrans et aux contenus longs.

Une hauteur fixe de 340 px n’est pas une obligation.
La lisibilité et l’accès aux actions priment.

### Implémentation

Inspecter les composants existants avant d’en créer un nouveau.
Éviter plusieurs implémentations concurrentes de FlipCard.

Si des classes CSS 3D personnalisées sont utilisées,
vérifier qu’elles sont réellement définies, par exemple :

.perspective-1000 { perspective: 1000px; }
.transform-style-3d { transform-style: preserve-3d; }
.backface-hidden {
  backface-visibility: hidden;
  -webkit-backface-visibility: hidden;
}
.rotate-y-180 { transform: rotateY(180deg); }

Ne pas modifier le comportement d’un carrousel existant
en confondant son défilement avec le retournement des cartes.

## 8. DÉFINITION D’UNE ACTION FONCTIONNELLE

Le libellé d’un bouton doit correspondre à son effet réel.

### Actions individuelles

- Détails : afficher l’élément sélectionné.
- Modifier : ouvrir son formulaire prérempli.
- Supprimer : demander une confirmation nommant cet élément,
  puis utiliser la logique de suppression autorisée.
- Voir un document : ouvrir le fichier correspondant.
- Imprimer : préparer une impression de l’élément concerné.

Une navigation vers une liste générale doit porter un libellé
tel que « Gérer les animaux », pas « Modifier ».

Les pages dédiées peuvent être réutilisées à condition
de prendre effectivement en charge l’identifiant et l’action.
Ne pas ajouter un paramètre que la destination ne traite pas.

### Formulaires et mutations

Prévoir :
- validation réellement exécutée ;
- état d’envoi visible ;
- prévention des doubles soumissions ;
- traitement des erreurs ;
- conservation de la saisie en cas d’échec ;
- succès annoncé seulement après confirmation de l’opération ;
- actualisation des données après réussite.

Ne pas fermer automatiquement un formulaire après un échec.
Ne pas présenter un échec d’audit ou de rafraîchissement
comme si l’écriture principale n’avait forcément pas eu lieu.

### États de l’interface

Traiter :
- chargement ;
- absence de données ;
- absence de résultat après filtrage ;
- erreur de chargement ;
- permission insuffisante ;
- action en cours.

Aucun bouton vide, faux succès ou lien de remplacement href="#".

Une action indisponible peut être désactivée avec une explication,
mais elle doit rester déclarée comme non livrée ou bloquée.

## 9. RÈGLES MÉTIER À PRÉSERVER

### Élevage

Ne pas inventer :
- règles d’effectif entre lots et animaux individuels ;
- compatibilités d’espèces ;
- règles de filiation ;
- conséquences automatiques des événements sur les statuts
  ou les effectifs.

Retrouver les règles existantes ou demander une décision ciblée.

Ne pas additionner les effectifs des lots et les animaux
individuels sans vérifier le sens métier de ce calcul.

### Opérations agricoles

Décisions acquises :
- une opération peut être liée à une parcelle ou à une campagne ;
- si une campagne est choisie, sa parcelle fait référence ;
- une contradiction campagne / parcelle doit être refusée ;
- les anciennes opérations non rattachées sont conservées ;
- aucune attribution automatique des données historiques.

Ces décisions ne prouvent pas que toutes les protections
correspondantes sont déjà implémentées ou validées.

### Recettes

« Recettes » signifie revenus financiers de l’exploitation.
Aucun concept de cuisine ne doit être introduit.

### Données sensibles

Ne pas élargir les accès existants aux informations de bailleurs
ou à d’autres données sensibles.

Ne pas supposer une valeur de rôle telle que 'admin' :
vérifier le modèle d’identité réellement utilisé.

Toute évolution de droits doit être traitée séparément,
avec contrôle côté base et validation explicite.

## 11. BASE DE DONNÉES, AUTH ET STORAGE

Distinguer :
- dépôt local ;
- environnement local de test ;
- environnement distant ;
- environnement de production.

Une application sur localhost peut utiliser une base distante.
Ne jamais considérer localhost comme preuve d’isolement des données.

Sans autorisation explicite :
- aucune migration appliquée ;
- aucun seed ;
- aucune modification RLS ;
- aucune modification de rôle ;
- aucune création, modification ou suppression distante de test ;
- aucun upload distant de test ;
- aucune suppression de fichier Storage.

Avant une mutation de test :
- identifier l’environnement ;
- confirmer qu’il est dédié et autorisé ;
- limiter les données concernées.

Ne pas afficher de secrets, mots de passe, jetons
ou chaînes de connexion sensibles.

Ne jamais affaiblir les droits pour faire réussir un test.

### Données simulées

Ne pas remplacer silencieusement une panne Supabase
par des données fictives.

Si un mode de démonstration est demandé :
- l’isoler explicitement ;
- afficher clairement qu’il s’agit d’une démonstration ;
- ne pas annoncer de persistance réelle ;
- ne pas mélanger données simulées et données réelles.

## 14. LIVRAISON ET CRITÈRES DE VALIDATION

Chaque livraison doit indiquer :

1. Résultat concret obtenu.
2. Fichiers créés ou modifiés.
3. Actions réellement raccordées.
4. Commandes exécutées et résultats.
5. Vérifications navigateur effectuées.
6. Vérifications de persistance effectuées, le cas échéant.
7. Limites et blocages restants.
8. Changements hors périmètre nécessitant un accord.

Utiliser des statuts précis :
- implémenté ;
- vérifié par lecture ;
- contrôlé automatiquement ;
- vérifié dans le navigateur ;
- testé avec persistance ;
- non vérifié ;
- bloqué.

Un lot est validé dans la limite des vérifications réalisées,
pas sur la seule base d’une affirmation.

Pour un lot frontend :
- navigation et actions cohérentes ;
- cartes utilisables sur ordinateur et mobile ;
- absence de régression constatée ;
- français et formatage cohérents ;
- contrôles exécutés et résultats rapportés.

Pour annoncer un parcours CRUD complet :
- vérifier les permissions ;
- exécuter le parcours dans un environnement autorisé ;
- confirmer la persistance après rechargement ;
- vérifier les erreurs et confirmations.
